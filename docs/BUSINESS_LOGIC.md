# Бизнес-логика и Сценарии (Edge Cases)

## 1. Механизм Gatekeeper (Web Portal)

Статус Gatekeeper **не требует отдельного HTTP-запроса**. Поля `is_verified` и `grace_period_left` возвращаются в ответе `POST /auth/login` и `GET /auth/me` и кешируются в `authStore`.

### Состояния
- **Верифицирован** (`is_verified = true`): страница рендерится без модального окна.
- **Мягкий блок** (`!is_verified && grace_period_left > 0`): показывается `<GatekeeperModal>` с двумя действиями.
- **Жёсткий блок** (`!is_verified && grace_period_left == 0`): показывается `<GatekeeperModal hardBlock>` — закрыть нельзя.

### Действия пользователя в модальном окне
Оба действия обрабатываются одним эндпоинтом `POST /profile/me/acknowledge`:
- **«Всё верно»** → `{ "action": "confirm" }` → `is_verified = true`, модальное окно закрывается.
- **«Пропустить»** → `{ "action": "skip" }` → `grace_period_left -= 1`, модальное окно закрывается.

### Закрытие Deadlock и предотвращение обхода (Bypass)
1. **Авто-верификация**: Если пользователь отправляет `POST /profile/me/change-request` из-под Gatekeeper-модального окна, это считается эквивалентом `action: "confirm"`: API автоматически устанавливает `is_verified = true`.
2. **Сброс при отклонении**: Если IT-Оператор отклоняет заявку пользователя (`PATCH /change-requests/{id}/reject`), и у этого пользователя **нет других активных** (`pending` или `conflict`) заявок, система обязана:
    - Установить `is_verified = false`.
    - Обнулить `grace_period_left = 0` (принудительный жёсткий блок).
    
Это гарантирует, что пользователь, подавший некорректные данные для обхода Gatekeeper, вернется в состояние жесткой блокировки после проверки данных оператором.

## 2. Статусы пользователей и поведение системы
- **ACTIVE** (Активен):
    - Отображается во всех видах поиска.
    - Доступ ко всем функциям системы.
    - Проходит стандартную проверку Gatekeeper.
- **RESIGNED** (Уволен):
    - **Скрыт** из поиска в Telegram-боте и на Web-портале.
    - Вход в систему **запрещен** (блокировка на уровне API Gateway).
    - Сохраняется в БД для истории заявок/репортов.
- **ON_LEAVE** (В отпуске / Отключен временно):
    - Отображается в поиске со специальной иконкой ⏳.
    - **Gatekeeper**: Проверки актуальности данных временно отключены для этого статуса (Hard Block не применяется).
    - Вход разрешен (если не заблокирован в AD).

## 3. Логика валидации (Контроль качества)
- **Обработка Telegram-репортов**: 
    - Репорт на профиль `is_protected = True` создает тикет тихо для IT, не меняя статус профиля.
    - Множественные репорты от разных пользователей меняют статус `change_requests` на `conflict`.

## 3. Ролевая модель (Панели управления)
- **IT-Operator**: Имеет доступ к "Пульту управления инцидентами". Разрешает записи со статусом `conflict`. Видит предупреждения о "двойном членстве" в организациях из `sync_error_log`. Может включить форсированную синхронизацию ("Force Sync").
