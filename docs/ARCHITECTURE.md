# Системная архитектура (Microservices)

Система построена на принципах микросервисной изоляции и разделения ответственности. Связь между микросервисами на первом этапе осуществляется через общую реляционную базу данных (PostgreSQL).

## 1. Сервис "API Gateway" (FastAPI)
- **Ответственность**: Обслуживание Web-интерфейса и внешних систем (включая Telegram-бот из отдельного проекта) по REST API.
- **Данные**: Читает и пишет только в PostgreSQL (Буферная БД). Не имеет прямого доступа к AD.
- **Логика**: Работа механизма Gatekeeper, проверка прав доступа, прием и агрегация репортов из Telegram-бота, нечеткий поиск (Fuzzy Search с использованием pg_trgm).

## 2. Сервис "AD Sync Worker" (Python + ldap3)
- **Ответственность**: Двунаправленная синхронизация данных между локальной PostgreSQL и Active Directory.
- **Данные**: Имеет доступ к PostgreSQL и права на чтение/запись в Active Directory.
- **Логика**: Опрос AD на изменения (Pull) с парсингом статуса из логина, и отправка одобренных заявок в AD (Push).
- **Отказоустойчивость**: Если AD недоступен, воркер переходит в режим ожидания (retry), API Gateway при этом продолжает штатно обслуживать пользователей.

15: ## 3. Инфраструктура User Presence (Redis Pub/Sub)
16: - **Ответственность**: Отслеживание статусов присутствия пользователей (online, away, offline) в реальном времени.
17: - **Механизм**:
18:   - При подключении пользователя к WebSocket-серверу API Gateway, статус пользователя сохраняется в глобальном Redis Hash `global_presence`.
19:   - Событие изменения статуса публикуется в Redis Pub/Sub канал `presence_updates`.
20:   - Все воркеры API Gateway подписаны на этот канал и транслируют обновления подключенным к ним клиентам по WebSockets.
21:   - При отключении пользователя статус обновляется на `offline` и удаляется из хэша.
