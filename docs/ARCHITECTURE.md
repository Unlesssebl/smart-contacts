# Системная архитектура (System Architecture)

Система «Smart Contacts» построена на принципах микросервисной изоляции, разделения ответственности, Event-Driven коммуникации и открытой наблюдаемости (Observability).

## 1. Сервис «API Gateway» (FastAPI)

* **Ответственность**: Обслуживание Web-интерфейса и внешних клиентов (включая Telegram-бот из отдельного проекта) по REST API и WebSockets.
* **Данные**: Читает и пишет только в локальную буферную БД PostgreSQL и кэш Redis. Прямого доступа на изменение AD у API Gateway нет.
* **Интерактивная документация**: Все эндпоинты, DTO, схемы валидации и статус-коды автоматически генерируются через OpenAPI:
  * Swagger UI: `/docs`
  * ReDoc: `/redoc`
  * OpenAPI JSON: `/openapi.json`
* **LDAP Интеграция**: Выделена в модульный пакет `app/core/ldap/`:
  * `connection.py` — Управление TLS (`PROTOCOL_TLS_CLIENT`) и пулом серверов AD.
  * `pool.py` — Управление соединениями с двойной проверкой блокировок (Double-Checked Locking).
  * `auth.py` — Процессы аутентификации, LDAP Injection защита и откат счетчиков brute-force при недоступности сети.
  * `search.py` — Поиск пользователей, маппинг OU.
  * `schemas.py` — Строгая Pydantic-типизация (`LdapUser`) и DRY маппинг атрибутов из Active Directory.
* **Масштабирование**: Синхронные блокирующие операции (LDAP, PostgreSQL) маршрутизируются в пул потоков (`anyio.to_thread`), чтобы не блокировать Event Loop. Долгосрочная стратегия перехода на нативный асинхронный стек описана в [ADR 0001: Async Migration](file:///c:/Users/belikov.a/Desktop/Акты,%20документы/Work/!Projects/smart-contacts/docs/adr/0001-async-migration.md).

## 2. Архитектура аутентификации и безопасности

* **Механизмы входа**:
  * **Kerberos SSO (SPNEGO)**: Бесшовный вход для доменных пользователей через эндпоинт `/auth/sso`.
  * **LDAP BIND**: Прямая проверка логина/пароля в Active Directory через `/auth/login`. Пароли пользователей никогда не сохраняются и не логируются в системе.
* **Управление сессиями**:
  * **Access Token (JWT)**: Короткоживущий токен (12 часов), содержащий `object_guid`, `sam_account_name` и `role`.
  * **Refresh Token**: Долгоживущий токен (30 дней), хэш которого хранится в таблице `refresh_tokens`. При ротации токена проверяется актуальный статус учетной записи в AD.
  * **Защита Cookies**: Токены передаются исключительно через защищенные `HttpOnly`, `Secure` (в prod), `SameSite=Lax` cookie.
* **CSRF-защита**:
  * Реализована по схеме Double Submit Cookie (`csrf_token` cookie + заголовок `X-CSRF-Token` для мутирующих HTTP-запросов `POST`, `PUT`, `PATCH`, `DELETE`).
* **Защита от Brute-Force и сетевая безопасность**:
  * Ограничение попыток входа и Rate Limiting реализованы через Redis.
  * Реальный IP клиента извлекается через `ProxyHeadersMiddleware` со строго доверенными хостами (`trusted_hosts`), исключая подмену заголовка `X-Forwarded-For`.

## 3. Сервис «AD Sync Worker» (Python + ldap3)

* **Ответственность**: Фоновая двунаправленная синхронизация данных между PostgreSQL и Active Directory.
* **Данные**: Имеет доступ к PostgreSQL и права на чтение/запись в Active Directory.
* **Логика работы**:
  * **Pull (AD → DB)**: Периодический опрос изменений по `uSNChanged`, парсинг статусов из суффиксов логина (`-uv` / `-time`) и флагов `userAccountControl`, извлечение структуры подразделений (OU).
  * **Push (DB → AD)**: Отправка одобренных оператором заявок на изменение контактных данных (`telephoneNumber`, `mobile`, `physicalDeliveryOfficeName`).
* **Отказоустойчивость**: При недоступности контроллеров домена воркер переходит в режим повторных попыток с экспоненциальной задержкой, не нарушая работу API Gateway.
* Подробные алгоритмы синхронизации и маппинга описаны в [docs/AD_INTEGRATION.md](file:///c:/Users/belikov.a/Desktop/Акты,%20документы/Work/!Projects/smart-contacts/docs/AD_INTEGRATION.md).

## 4. Инфраструктура реального времени (Redis Pub/Sub & WebSockets)

* **Отслеживание статусов (Presence)**:
  * При подключении к WebSocket статус пользователя (`online`, `away`, `offline`) записывается в Redis Hash `global_presence`.
  * Событие публикуется в канал Redis Pub/Sub `system_events` (`presence_update`) и транслируется всем инстансам API Gateway.
* **Системные события (Event-Driven Updates)**:
  * События изменений профилей, модерации заявок (`admin_update`, `profile_updated`) доставляются на фронтенд мгновенно без поллинга.
* **Устойчивость к нагрузкам (Highload)**:
  * Клиентский WebSocket использует алгоритм **Exponential Backoff с джиттером** для предотвращения эффекта лавины (Thundering Herd) при перезапусках бэкенда.
  * Серверная рассылка использует неблокирующий `asyncio.gather`.

## 5. Слой данных (Shared Models & Storage)

* **PostgreSQL 15**: Основное хранилище. Для устранения дублирования кода оба сервиса (`api_gateway` и `ad_sync_worker`) используют общий пакет `services/shared/models`.
* **Alembic**: Управление миграциями схемы БД.
* **Нечеткий поиск**: Полнотекстовый и нечеткий поиск по ФИО, телефонам и подразделениям реализован с помощью расширения PostgreSQL `pg_trgm`.

## 6. Мониторинг и наблюдаемость (Observability Architecture)

Архитектура системы изначально спроектирована для работы с **централизованным корпоративным стеком мониторинга** (Prometheus & Grafana):

* **Экспорт метрик**: `api_gateway` содержит встроенный инструмент `prometheus-fastapi-instrumentator` и публикует метрики в формате OpenMetrics по стандартному адресу `/metrics`.
* **Централизованный сбор**: Выделенный сервер Prometheus периодически опрашивает (pull) эндпоинты `/metrics` системы `smart-contacts` и других смежных корпоративных сервисов.
* **Дашборд как код (Dashboard-as-Code)**: В репозитории в каталоге `monitoring/grafana/dashboards/` поддерживается готовый JSON-шаблон дашборда для мгновенного импорта в центральную Grafana.
* **Локальный Dev-стек**: Для локальной отладки в репозитории сохранены конфигурации автономного запуска Prometheus и Grafana. Подробнее см. [monitoring/README.md](file:///c:/Users/belikov.a/Desktop/Акты,%20документы/Work/!Projects/smart-contacts/monitoring/README.md).
