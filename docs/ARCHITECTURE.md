# Системная архитектура (Microservices)

Система построена на принципах микросервисной изоляции и разделения ответственности. Связь между микросервисами осуществляется через общую реляционную базу данных (PostgreSQL). Для предотвращения рассинхрона схем БД и дублирования кода используется единый пакет `services/shared/models`, который переиспользуется обоими сервисами.

## 1. Сервис "API Gateway" (FastAPI)
- **Ответственность**: Обслуживание Web-интерфейса и внешних систем (включая Telegram-бот из отдельного проекта) по REST API.
- **Данные**: Читает и пишет только в PostgreSQL (Буферная БД). Не имеет прямого доступа к AD.
- **Логика**: Работа механизма Gatekeeper, проверка прав доступа, прием и агрегация репортов из Telegram-бота, поиск по ФИО и телефонам (с использованием pg_trgm для ранжирования).
  - **LDAP Интеграция**: Выделена в модульный пакет `app/core/ldap/`:
    - `connection.py` — Управление TLS (`PROTOCOL_TLS_CLIENT`) и пулом серверов AD.
    - `pool.py` — Управление соединениями с двойной проверкой блокировок (Double-Checked Locking).
    - `auth.py` — Процессы аутентификации, LDAP Injection защита и откат счетчиков brute-force при недоступности сети.
    - `search.py` — Поиск пользователей, маппинг OU.
    - `schemas.py` — Строгая Pydantic-типизация (`LdapUser`) и DRY маппинг атрибутов из Active Directory.
  - **Масштабирование**: Синхронные блокирующие операции (LDAP, PostgreSQL) маршрутизируются в Threadpool, чтобы не блокировать Event Loop. Подробный план будущей миграции на `asyncio` описан в `docs/ASYNC_MIGRATION_NOTE.md`.
  - **Безопасность**: Защита от Brute-Force атак использует реальные IP клиентов через `ProxyHeadersMiddleware`.

## 2. Сервис "AD Sync Worker" (Python + ldap3)
- **Ответственность**: Двунаправленная синхронизация данных между локальной PostgreSQL и Active Directory.
- **Данные**: Имеет доступ к PostgreSQL и права на чтение/запись в Active Directory.
- **Логика**: Опрос AD на изменения (Pull) с парсингом статуса из логина, и отправка одобренных заявок в AD (Push).
- **Отказоустойчивость**: Если AD недоступен, воркер переходит в режим ожидания (retry), API Gateway при этом продолжает штатно обслуживать пользователей.

## 3. Инфраструктура Реального Времени (Redis Pub/Sub & WebSockets)
- **Ответственность**: Отслеживание статусов присутствия пользователей (online, away, offline) в реальном времени, а также мгновенная доставка системных обновлений (Event-Driven Architecture).
- **Механизм Presence**:
  - При подключении пользователя к WebSocket-серверу API Gateway, статус пользователя сохраняется в глобальном Redis Hash `global_presence`.
  - Событие изменения статуса публикуется в Redis Pub/Sub канал `system_events` с типом `presence_update`.
  - Все воркеры API Gateway подписаны на этот канал и транслируют обновления подключенным к ним клиентам по WebSockets.
  - При отключении пользователя статус обновляется на `offline` и удаляется из хэша.
- **Механизм Системных Событий**:
  - API Gateway и AD Sync Worker публикуют события (например, `admin_update`, `profile_updated`, `ldap_status_updated`) в канал `system_events`.
  - Фронтенд-клиенты получают эти события по WebSockets и реактивно обновляют UI без использования ресурсоемкого HTTP-поллинга.
  - Высокая нагрузка (Highload) обрабатывается за счет использования алгоритма **Exponential Backoff с джиттером** на клиенте (защита от Thundering Herd при перезапусках API) и параллельной рассылки (через `asyncio.gather`) на сервере, что предотвращает блокировку Event Loop.
